# D-059 — Windows code-signing and publication boundary

- **Status:** Proposed
- **Date:** 2026-08-18
- **Stage:** Stage 9 Desktop Productization & Release Hardening

## Context

D-057 and D-058 close the Stage 9 product/runtime evidence and Windows media redistribution boundaries, but a public Windows release still needs a real trusted code-signing identity, exact verification of the signed bytes and post-signing artifact checksums.

Signing must not become a new source of ambient authority. UV Studio carries third-party FFmpeg/MLT/Qt/runtime binaries whose provenance is already reviewed under D-058; acquiring a UV certificate is not permission to silently re-sign those third-party files. The release therefore needs a small explicit signing boundary that is independent of the signing provider and can be tested without putting a private key into ordinary pull-request CI.

Self-signed test certificates are useful only for local implementation experiments and are not accepted as public-release evidence.

## Proposed decision

Define the public Windows signing contract in `packaging/windows-signing-policy.windows-x86_64.json` and enforce it through `tools/windows_signing_boundary.py`.

The public policy contains exactly three UV-owned signing targets:

1. `backend/uv-studio-backend.exe` — sign after final backend/release staging but **before D-044** builds the immutable payload manifest;
2. the NSIS-generated uninstaller executable — sign through NSIS `!uninstfinalize` while the installer is being compiled;
3. `uv-studio-windows-x86_64-setup.exe` — sign after installer construction.

The policy explicitly forbids expanding a release-file signing target into `runtime/**`, `frontend/**` or `backend/_internal/**`. In particular, the carried FFmpeg/MLT/Qt/codec DLL graph is not re-signed with the UV identity.

The signing implementation is provider-neutral. A future public signer may be a certificate-backed local `signtool`, a hardware-backed service or a hosted signing service, but provider credentials and transport are outside canonical release/project state. The verifier only receives the resulting file plus the expected public certificate identity.

## Fail-closed verification

`tools/windows_signing_boundary.py` provides three operations:

- `validate-policy` — validates the exact signing target/phase/publication contract;
- `snapshot` — records size and SHA-256 of the exact unsigned target before an external signer changes it;
- `verify` — uses Windows Authenticode inspection to require a valid signature, expected publisher subject, optional expected publisher thumbprint and a timestamp certificate, while proving that the signed bytes differ from the recorded pre-sign bytes.

The verifier writes bounded secret-free JSON evidence containing only target identity, pre/post hashes, sizes and public certificate/timestamp identity. It does not write a private key, signing token, password or provider credential into the release payload.

A `release_file` target must resolve to its exact policy path beneath the supplied release root. Artifact targets must match their exact basename. The generated uninstaller target is constrained to an executable and is additionally bound by the NSIS-only phase.

## NSIS boundary

`packaging/windows/uv-studio.nsi` exposes opt-in guarded hooks:

- `UV_SIGN_INSTALLER_COMMAND` through `!finalize`;
- `UV_SIGN_UNINSTALLER_COMMAND` through `!uninstfinalize`.

The command must accept the generated executable path as its final argument and return success. Existing PR/release evidence does not define either symbol, so the ordinary Stage 9 workflow remains genuinely unsigned rather than fabricating trust evidence.

A future public-release workflow will supply a real signing command and then run the UV verifier against the resulting installer/uninstaller.

## Publication order

The required public-release order is:

`build backend -> stage final runtime -> snapshot/sign/verify UV backend -> build D-044 manifest -> build installer with signed uninstaller -> sign/verify installer -> archive exact signed portable payload -> SHA256SUMS -> publish`

This order is intentional:

- signing changes executable bytes, so the backend must be signed before D-044 hashes the payload;
- the uninstaller is generated by NSIS and therefore must be signed during installer construction;
- the outer installer is signed only after it is fully built;
- final artifact checksums must describe the signed bytes, never the unsigned candidates.

`tools/write_release_checksums.py` remains the deterministic checksum authority and is not moved earlier in the pipeline.

## Acceptance criteria

D-059 may become **Accepted** only when one exact public-release head proves all of the following:

1. the checked-in signing policy still contains exactly backend, generated uninstaller and installer targets;
2. no third-party runtime/frontend/`backend/_internal` file is signed as a UV public target;
3. the backend has valid Authenticode from the expected UV publisher before D-044 is created, and D-044 deep verification succeeds on those signed bytes;
4. the generated installed uninstaller has valid Authenticode from the expected UV publisher;
5. the final installer has valid Authenticode from the expected UV publisher;
6. all required signatures contain accepted timestamp-certificate evidence;
7. silent install, installed launch, safe uninstall and A -> B -> A update/rollback remain green with the signed candidates;
8. `SHA256SUMS` is generated only after all signatures and verifies against the exact published portable archive and installer;
9. signing evidence contains no private credential material;
10. the exact acceptance head passes every permanent CI job and the signed Windows publication workflow.

Until those criteria are demonstrated with a real public signing identity, D-059 remains **Proposed** and PR #38 remains Draft.

## Consequences

- UV can change signing providers without changing canonical project semantics or the set of files UV owns and signs.
- Ordinary pull requests do not need access to a production signing key.
- Third-party media/runtime provenance remains governed by D-058 rather than being obscured by a UV signature.
- A certificate renewal or signing-provider migration must preserve the checked-in target boundary and update expected public identity evidence explicitly.
- The final whole-payload dependency/security/license audit remains a separate Stage 9 blocker even after D-059 mechanics are implemented.
